## 1. 무엇을 만드는가

사고 당사자가 아는 기초 정보(진단명, 수술 여부, 입원·통원 기간, 과실비율, 직업·소득, 차량 수리비 등)와 가입한 보험증권만으로, 담보별 예상 보험금을 사람별로 추정해 보여준다.
결과는 "사람 × 담보" 표 하나이고, 칸마다 최소·예상·최대 세 값과 계산 근거가 붙는다.

대상 약관: 개인용·업무용·영업용 자동차보험, 이륜자동차보험.
택시·버스·화물 공제조합의 공제약관은 보험약관이 아니므로 이번 범위에 넣지 않는다. 상대방이 공제조합 가입 차량이면 "상대방 계약 확인 필요"로 표시한다.
운전자보험 증권은 보험사·상품 종류·담보·가입금액을 읽어 보여주지만, 계산 규칙이 없으므로 "증권에 있으나 계산 규칙 미등록"으로 표시하고 합계에 넣지 않는다.

정해 둔 것:

- 디자인: 흰 배경, 남색 포인트 1색, 카드형, 큰 글씨, 한 화면에 한 가지 일, 하단 고정 "다음" 버튼, 단계 표시(1/4 …). v1 그대로.
- 진행 중 입력과 결과는 고칠 때마다 브라우저 `localStorage`에 자동 저장된다(v1 `lib/draft`). 서버로 저장하는 단계는 없다.
- 첫 화면과 내 사고 기록 화면에 "기록은 이 기기의 이 브라우저에만 남고 서버에는 저장되지 않습니다. 브라우저 기록을 지우면 다시 볼 수 없으니 결과를 엑셀·PDF로 받아 두세요" 안내.
- "내 보험" 화면의 증권 표에는 보험사·상품 종류·보험기간·차종·연식·차량가액·운전자 범위·연령 한정·담보(가입금액·자기부담금)·특약만 나온다. 이름·증권번호·차량번호 칸은 없다. 가린 것이 있으면 "개인정보 ○건을 가렸습니다"만 알려 준다.
- 올리기 전 안내: "이름·주민번호·차량번호 부분을 가리고 찍으면 더 안전합니다." 사진은 올리기 전에 가리기 화면을 거친다. 화면 위쪽에 "이름·주민번호·증권번호·차량번호를 칠해 주세요"를 크게 띄우고, 손가락으로 칠한 부분은 그림 자체에서 검게 바뀐 뒤 올라간다. 아무것도 칠하지 않고 올리면 "가린 곳이 없습니다. 그대로 올릴까요?" 확인창을 한 번 더 띄운다(5단계).
- 사람 카드의 제목은 역할 이름이다("운전자(나)", "동승자 1", "상대 차 운전자", "보행자"). 이름을 넣는 칸은 없다. 사고 말하기 화면에 "사람 이름은 말하지 않아도 됩니다" 안내.
- 건강정보 동의 없이도 진단·수술을 직접 입력해 계산할 수 있다(계산은 브라우저 안에서 한다). 음성 변환·사고 사실 추출은 건강정보가 서버·LLM으로 가므로 건강정보 동의가 필요하다.
- 유료 기능 버튼 옆에 "오늘 남은 횟수 ○회"를 보여 준다. 다 쓰면 "오늘 사용 횟수를 다 썼습니다. 직접 입력해 계산할 수 있어요"를 보여 주고, 직접 입력과 계산은 계속 쓸 수 있다.
- 결과 표의 칸 표시는 네 가지다.
  - 금액: 최소 · 예상 · 최대
  - 정보 부족: "○○을 입력하면 계산됩니다" (누르면 해당 입력 칸으로 이동)
  - 해당 없음: 이 사람에게 이 담보가 적용되지 않는 이유
  - 약관 확인 필요: 규칙이 `needs_check`이거나 사고일에 맞는 규칙이 없을 때
- 합계는 받는 사람 묶음별로 따로 보여준다. "내가 받을 예상액"과 "상대방에게 지급될 예상액"을 하나로 더하지 않는다.
- 모든 결과 화면 하단: "참고용 추정이며 손해사정이나 보험금 지급 확정이 아닙니다"

## 3. 로그인 없이 유료 API 남용 막기

### 무엇을 "1회"로 셀 것인가 (확정)

사고 한 건을 처리하려면 유료 호출이 여러 번 필요하다(증권 읽기 1~2, 음성 변환 1~3, 사실 추출 1~2, 설명·읽어주기 여러 번). 호출 하나를 1회로 세면 IP당 하루 3회로는 사고 한 건도 끝낼 수 없다. 그래서 다음과 같이 정했다.

- **1회 = 분석 이용권 1장.** 유료 기능을 처음 누를 때 Turnstile을 거쳐 이용권을 받는다. IP당 하루 3장(한국 시각 자정에 다시 생긴다).
- 이용권은 서버 비밀값(`GUARD_SECRET`)으로 HMAC 서명한 짧은 문자열(`kc2t1.<내용>.<서명>`)이고, 유효 시간은 2시간이다. 내용은 번호·발급·만료 시각·`plan: "free"`뿐이다(IP·사람 정보 없음). 브라우저 `sessionStorage`(`kc2.ticket`)에만 둔다.
- 이용권 1장으로 쓸 수 있는 경로별 횟수: 증권 읽기 3, 음성 5, 사고 내용 추출 5, 설명 10, 읽어주기 10(`TICKET_CALL_LIMITS`로 바꿀 수 있다).

### 카운터 저장소: Upstash Redis (4단계에서 바꾼 결정, 2026-10-14)

1단계에서는 추가 서비스 없이 서명 쿠키 + Vercel Firewall로 가기로 했다. 4단계를 시작하며 다시 따져 보니 두 가지가 맞지 않아 사용자 확인을 받고 Upstash Redis(Vercel 마켓플레이스, 무료 등급 월 50만 명령·256MB)로 바꿨다.

1. 무료 요금제(Hobby)의 Vercel Firewall 사용자 규칙은 프로젝트당 3개다. 계획한 6개(발급 1 + 유료 경로 5)를 둘 수 없다.
2. 쿠키 카운터로는 이용권 재사용(옛 쿠키를 다시 보내기)과 같은 파일 중복 과금을 서버에서 막을 수 없다.

그래서 `@vercel/firewall`과 쿠키 카운터는 쓰지 않는다. Redis에는 사용자 기록이 아니라 개수와 표시만 두고, 모든 키는 하루 안쪽에 저절로 사라진다(`lib/guard/store.ts`). npm 패키지는 더하지 않고 Upstash REST API(`/pipeline`)를 `fetch`로 부른다.

| 키 | 내용 | 사라지는 때 |
|---|---|---|
| `kc2:day:<IP HMAC>:<한국 날짜>` | 오늘 발급한 이용권 수 | 2일 |
| `kc2:try:<IP HMAC>:<한국 시각 시>` | 발급 시도 수(시간당 20번) | 1시간 |
| `kc2:ts:<토큰 HMAC>` | 이미 쓴 Turnstile 토큰 | 10분 |
| `kc2:tk:<이용권 번호>` | 이 서버가 발급한 이용권 | 이용권 만료 |
| `kc2:use:<번호>:<경로>` | 경로별 쓴 횟수 | 이용권 만료 |
| `kc2:all:<번호>` | 돌려받은 것까지 합친 전체 시도 수(경로별 횟수 합의 2배까지) | 이용권 만료 |
| `kc2:fast:<번호>:<경로>` | 연속 요청 간격(증권·음성·추출 3초, 설명·읽어주기 1초) | 그 간격 |
| `kc2:file:<번호>:<파일 HMAC>` | 같은 이용권으로 같은 파일을 읽은 번수 | 이용권 만료 |

IP 원문, 사고 내용, 건강정보, 증권 내용, 판독 결과는 Redis에 넣지 않는다. IP는 요청을 받자마자 `GUARD_SECRET`으로 HMAC한 값만 쓴다.

- 로컬 개발: Upstash 설정이 없으면 메모리 카운터를 쓴다(한 프로세스). `GUARD_DEV_CLOCK_FILE`에 적은 밀리초만큼 서버 시계를 옮겨 "다음 날"을 시험할 수 있다(메모리 카운터일 때만).
- 배포(`VERCEL`): Upstash 설정이 없으면 유료 기능을 막는다. Turnstile 시험용 키가 `VERCEL_ENV=production`에 들어가도 막는다.
- 알아 둘 점: 휴대폰 통신사 망은 여러 사람이 IP 하나를 함께 쓰는 경우가 많다. IP당 하루 3장이면 같은 IP의 다른 사용자가 막힐 수 있다. 문제가 보이면 `DAILY_TICKET_LIMIT`를 올린다.
- 마지막 방어선: OpenAI 프로젝트 예산·Anthropic 워크스페이스 사용 한도를 월 금액으로 건다(11단계).

### 처리 순서

이용권 발급(`issueTicket`, `/api/guard/ticket`): 서비스 동의 버전 → 발급 시도 시간당 20번 → 오늘 남은 장수(없으면 Turnstile을 부르지 않고 429) → 같은 Turnstile 토큰 재사용 거절 → Cloudflare `siteverify` → 발급 기록. Turnstile 시험용 비밀 키(`1x…AA` 등)는 매번 같은 가짜 토큰을 주므로 재사용 검사만 건너뛴다.

유료 라우트(`paidGuard(request, 경로 id, 필요한 동의)`):

1. 설정·저장소가 없으면 503 "지금은 자동 기능을 쓸 수 없습니다. 직접 입력해 계산할 수 있어요."
2. 요청 머리글 `x-kc2-consent`의 동의 버전. 서비스 동의가 없으면 403, 건강정보 경로(음성·추출·설명)는 건강정보 동의가 없으면 403.
3. 머리글 `x-kc2-ticket`의 이용권: 없음·위조·만료면 401, 서명이 맞아도 발급 기록이 없으면 401.
4. 연속 요청 간격, 전체 시도 수, 이 경로의 남은 횟수. 넘으면 429.
5. 통과하면 1회를 깎고 제공자를 부른다. 결과를 돌려주지 못하면(입력 오류, 제공자 설정 없음·장애) 라우트가 `refund()`로 돌려준다. 설명에서 LLM을 부르지 않은 경우도 돌려준다.
6. 증권 읽기는 파일을 받은 뒤 `sameFile()`을 부른다. 같은 이용권으로 같은 파일을 다시 읽으면 2번까지 횟수를 깎지 않는다. 화면도 이 탭에서 읽은 파일의 결과를 메모리에 두고(`lib/upload/reading-cache.ts`, 5개까지) 같은 파일은 서버에 다시 보내지 않는다.

막힌 요청은 제공자를 부르기 전에 끝난다. `tests/paid-routes.test.ts`가 `app/api`의 모든 라우트를 찾아, 공개 라우트 4개(`guard/config`, `guard/ticket`, `laws`, `laws/precedents`)가 아닌 라우트는 자기 경로 id로 `paidGuard`를 제공자 호출보다 먼저 부르는지 보고, 실제로 불러 이용권 없음·위조·만료·발급 기록 없음·동의 없음·횟수 소진이 제공자 호출 0번으로 거절되는지 확인한다. 서버 코드에 `console` 출력이 있으면 실패한다.

### 결제를 붙일 자리 (이번에는 만들지 않음)

이용권 내용의 `plan`은 지금 `"free"`뿐이다. 결제를 붙이면 결제 확인 뒤 `plan: "paid"` 이용권을 발급하는 경로를 `/api/guard/ticket` 옆에 따로 두고, 하루 무료 장수와 따로 센다(`issueTicket`의 주석). 문지기(`checkPaid`)는 `plan`에 따라 경로별 횟수만 바꾸면 된다.

v1에서 없애는 것: `app/api/auth/`, `app/auth/callback/`, `app/login/`, `components/LoginForm.tsx`, `lib/auth/`(Supabase 클라이언트·`paidUser()`·하루 한도 RPC), `proxy.ts`의 세션 갱신, `supabase/migrations/`, PGlite RLS 테스트, `@supabase/*`·`@electric-sql/pglite` 패키지.

## 4. 저장

### 서버

서버는 아무것도 저장하지 않는다. DB 테이블이 없다. 남는 것은 다음뿐이다.

- 법령·판례 응답의 메모리 캐시(24시간, 개인정보 없음)
- Upstash Redis의 이용권·사용량 카운터(3절 표. IP HMAC·이용권 번호·파일 HMAC과 개수뿐, 하루 안쪽에 사라짐)
- Vercel 요청 로그: 경로·상태 코드·시간만. 앱은 요청 본문을 로그에 쓰지 않는다

### 브라우저 (`lib/draft`)

| 키 | 내용 | 비고 |
|---|---|---|
| `kc2.consent` | 서비스·건강정보 동의 버전과 날짜 | 동의 문구 버전이 바뀌면 다시 묻는다 |
| `kc2.case.<id>` | 증권(보험 정보만)·사고·사람 입력 초안 | 신원 칸 없음. 읽을 때 zod `strict`(`lib/draft/schema.ts`)로 검증하고 실패하면 그 사고를 "읽을 수 없는 기록"으로 표시. 사고 목록은 따로 키를 두지 않고 이 키들에서 바로 만든다(목록과 초안이 어긋나지 않게, 3단계에서 정함) |

- 이용권은 `sessionStorage`의 `kc2.ticket`(탭을 닫으면 사라짐)에 둔다. 오늘 남은 장수는 저장하지 않고 `/api/guard/config`에서 그때그때 받는다(계획의 `kc2.quota`는 만들지 않았다).
- 증권 읽기 결과는 같은 파일을 다시 쓰기 위해 이 탭의 메모리에만 둔다(브라우저 저장소에 넣지 않는다).
- 원본 이미지·PDF·음성, 전사문 원문은 저장하지 않는다. 전사문은 `redact.ts`를 거친 사고 설명 글로만 남는다.
- "이 기기의 기록 모두 지우기"는 `kc2.` 로 시작하는 키(동의 기록 포함)와 옛 키 `kac:draft:`를 모두 지우고, 이 탭의 이용권과 증권 읽기 결과도 버린다.
- 옛 키 `kac:draft:<id>`(v1·2단계)의 초안은 처음 읽을 때 신원 칸을 버리고 `kc2.case.<id>`로 옮긴다.
- 건강정보 동의를 철회하면 모든 사고의 사람 칸에서 다친 내용·진단명·상해급수·수술·입원·통원 일수·치료비를 지운다(`HEALTH_FIELDS`).
- 동의 화면의 체크박스는 저장된 동의 기록으로만 처음 상태를 정하고, 미리 체크하지 않는다(`tests/consent-form.test.ts`).

| 라우트 | 메서드 | 필요 조건 | 하는 일 |
|---|---|---|---|
| `/api/guard/config` | GET | – | 유료 기능을 쓸 수 있는지, Turnstile 사이트 키, 오늘 남은 이용권 수(IP 기준), 이용권 1장의 경로별 횟수 |

경로별 한도는 Vercel Firewall 규칙이 아니라 이용권별 Redis 카운터로 센다(3절). Firewall 규칙은 두지 않아도 되고, 둔다면 무료 요금제 한도(3개) 안에서 `/api/guard/ticket` 하나에만 IP 기준 규칙을 더한다(11단계). 업로드 제한: 증권은 PDF·HEIC·JPEG·PNG(파일 이름이 아니라 첫 바이트로 판별), 4MB, PDF 3쪽까지. 음성은 4MB·5분. 사고 글은 5,000자.

v1에서 없애는 환경변수: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `DAILY_*_LIMIT`(사용자별). 모델 이름은 코드에 쓰지 않고 환경변수로 둔다.

### 증권 읽기의 처리 순서 (가린 뒤에만 분석)

1. 형식 판별: 파일 이름이 아니라 첫 바이트로 PDF·JPEG·PNG·HEIC를 가린다(`lib/extract/file.ts`).
2. 사진은 올리기 전에 브라우저에서 사용자가 이름·번호 부분을 칠해 가린다(2절). 칠한 부분은 그림 자체에서 검게 바뀐 뒤에 올라간다.
3. **글자가 있는 PDF**: `unpdf`로 글자를 뽑고 `redact.ts`로 가린 뒤, **가린 글자만** LLM에 보낸다. 그림은 보내지 않는다. 이 경로에서는 신원정보가 서버 밖으로 나가지 않는다.
4. **사진·스캔 PDF**(글자 50자 미만): HEIC는 JPEG로, `sharp`로 회전을 바로잡고 긴 변 2000px로 줄인 뒤 비전 LLM에 보낸다. 그림 속 글자는 서버가 미리 가릴 수 없으므로, 그림을 읽는 일(인식) 자체는 비전 LLM이 한다. 그래서 2번의 칠해 가리기와 "가리고 찍으면 더 안전합니다" 안내를 둔다. 비전 LLM에는 "이름·주민번호·증권번호·차량번호·주소·전화·이메일·계좌·카드번호는 읽지도 적지도 말라"고 지시한다.
5. 비전 LLM은 `lib/schemas/policy-reading.ts`의 모양으로만 답한다. 스키마에는 신원 칸이 없다. zod `strict` 검증에 실패하면 한 번만 다시 시킨다.
6. 서버가 응답 전체 문자열을 `redact.ts`로 한 번 더 거른다. LLM이 담보 원문(`sourceText`) 같은 다른 칸에 번호를 적어도 여기서 걸린다. 가린 건수만 화면에 알린다.
7. 화면은 읽은 보험 정보를 표로 보여 주고, 읽지 못한 칸(null)은 노란색 "확인 필요"로 표시한다.

금액·한도·자기부담금은 증권에 적힌 표현 그대로 둔다. 원 단위 변환은 `money.ts`가 한다.

### 가리기 (`lib/privacy/redact.ts`)

| 대상 | 잡는 방법 | 가리면 안 되는 것(오탐 테스트) |
|---|---|---|
| 주민등록번호 | `\d{6}-?[1-8]\d{6}`, 뒷자리 일부를 `*`로 가린 꼴 | 날짜 `2026-09-01`, 금액 |
| 외국인등록번호 | 주민번호와 같은 꼴(뒷자리 5~8) | |
| 전화번호 | `01[016789]-?\d{3,4}-?\d{4}`, 지역번호 꼴, `1588-0000` 같은 대표번호는 남김(보험사 콜센터) | 보험사 대표번호 |
| 이메일 | 일반 이메일 꼴 | |
| 차량번호 | `(지역명)?\d{2,3}[가-힣]\d{4}` | "3천만원", "7급" |
| 증권번호 | 숫자·영문·하이픈 묶음 10자리 이상(쉼표 없음), "증권번호" 항목 뒤의 값 | `30,000,000`(쉼표 금액) |
| 계좌번호 | 하이픈으로 나뉜 숫자 묶음 10~14자리, "계좌·예금주" 항목 뒤의 값 | |
| 카드번호 | 13~19자리(공백·하이픈 허용) + Luhn 검사 | |
| 이름 | "계약자·피보험자·성명·운전자명·예금주·기명피보험자" 항목 이름 뒤의 한글 2~5자 | 담보 이름("자기신체사고") |
| 주소 | "주소·소재지" 항목 뒤의 한 줄, `○○시 ○○구 ○○로 12` 꼴 | |

항목 이름이 없이 문장 속에 섞인 이름·주소는 정규식으로 다 잡지 못한다. 그래서 판독 스키마와 추출 스키마에 이름·주소 칸을 두지 않는 것이 첫 방어이고, `redact.ts`는 두 번째 방어다.

### 상해급수 후보 (v1 5단계에서 구현)

- `data/rules/injury-grade-map.json`: 자동차손해배상보장법 시행령 [별표 1]의 상해 내용 248개 항목(1~14급). 현대해상 개인용 약관(2025-11-26 개정) <붙임> 85~90쪽에서 `scripts/build-injury-grade-map.mjs`가 글자를 그대로 뽑았다. 항목마다 근거 조항(○급 ○호)과 쪽 번호가 있다.
- 항목 문구는 `confirmed`(PDF에서 그대로 뽑음, 사람이 한 줄씩 대조하지는 않음). 별표의 시행일과 진단명 검색용 낱말(동의어)은 `needs_check`.
- `lib/engine/injury-grade.ts`의 `suggestInjuryGrades()`가 진단명·수술 여부로 후보와 이유를 낸다. 별표에 입원일수 기준이 없어 입원일수는 쓰지 않는다. 같은 별표의 "2. 영역별 세부지침"(병급, 보존적 치료 시 하향 등)은 반영하지 않는다.
- 후보는 확정이 아니다. 사용자가 고른 급수(`injuryGrade`)만 뒤 단계의 계산에 쓴다.

## 6. 계산 엔진 (`lib/engine`)

### 계산 순서

```
증권 JSON ┐
사고 JSON ├─▶ ① 검증 ─▶ ② 규칙 고르기 ─▶ ③ 사람별 손해 항목 ─▶ ④ 담보별 칸 ─▶ ⑤ 담보 사이 조정 ─▶ ⑥ 행렬·합산
사람 JSON ┘                (사고일 기준)       (손해 장부)
```

핵심은 ③의 손해 장부다. 사람마다 손해 항목(치료관계비, 위자료, 휴업손해 등)을 한 번만 만든다. 담보 모듈은 이 장부의 항목을 가져다 한도·과실·공제를 적용할 뿐, 손해를 새로 만들지 않는다. 같은 손해 항목이 여러 담보 칸에 나타나면 ⑤에서 한 경로만 합계에 넣는다.

### 공통 모듈

| 모듈 | 하는 일 |
|---|---|
| `money.ts` | "3천만원", "1억", "30,000,000" 같은 표현을 원 단위 정수로. 모호하면 `null`. "무한"은 별도 값 |
| `decimal.ts` | 비율 곱하기, 과실상계, 원 미만 처리. `decimal.js`를 쓰는 유일한 곳 |
| `range.ts` | 최소·예상·최대 세 값의 덧셈, 한도 적용, 비교 |
| `rules.ts` | 규칙 묶음에서 id로 값을 꺼낸다. `needs_check`이면 값과 함께 표시를 돌려준다 |
| `applicability.ts` | 이 담보가 이 사람·이 증권에 해당하는지. 운전자 범위·연령 한정 위반, 음주·무면허, 보험기간 밖 사고를 여기서 걸러 "해당 없음" 또는 "약관 확인 필요"로 만든다 |
| `injury-grade.ts` | 진단명·수술 여부로 상해급수 후보를 찾는다(자동차손해배상 보장법 시행령 별표의 상해 구분). 하나로 정해지지 않으면 급수 범위를 돌려주고, 이것이 최소·최대 값의 차이가 된다. 사용자가 급수를 알면 그 값을 쓴다 |

| `loss-ledger.ts` | 사람별 손해 항목 장부를 만든다 |
| `coordinate.ts` | 담보 사이 조정: 대인Ⅰ·Ⅱ 나누기, 자동차상해에서 대인 지급액 공제, 같은 손해의 대체 경로 표시 |
| `accident.ts` | 사람·차량·특약 칸을 모아 사람 × 담보 행렬을 만든다. 보험 종류의 약관에 없는 담보·특약을 걸러 낸다 |
| `summarize.ts` | 행렬의 칸에서 사람별·담보별·총합계를 낸다. 합계를 내는 유일한 함수. 받는 사람 묶음(mine / others)마다 따로 내고 두 묶음은 더하지 않는다 |
| `trace.ts` | 칸마다 계산 단계를 사람이 읽을 수 있는 내역으로 남긴다(쓴 값, 쓴 규칙 id, 식) |

### 사람 담보 사이의 관계 (v1 6단계에서 구현)

한 사람의 같은 손해를 여러 담보가 보상할 수 있다. `lib/engine/coordinate.ts` 한 곳에서 아래 순서로 계산하고, 뒤 담보는 앞 담보의 금액을 뺀다. 그래서 계산된 칸끼리는 금액이 겹치지 않는다.

| 순서 | 담보 | 누구의 보험 | 계산 | 근거 |
|---|---|---|---|---|
| ① | 대인배상Ⅰ | 가해 차량 | 부상·후유장애·사망 각각: 손해액 × (100 − 과실)% → 부상은 치료비 보장, 사망은 최저 2,000만원 → 급별·사망 한도 | 제10조, 별표4, 시행령 별표1·2 |
| ② | 대인배상Ⅱ | 가해 차량 | 세 구분을 합한 손해액 × (100 − 과실)% → 치료비 보장(12~14급 차량운전자는 대인Ⅰ 한도를 넘는 치료비에 본인 과실만큼 부담) → ① 공제 → 가입금액 | 제10조, 별표4 1.가.(3) |
| ③ | 무보험자동차상해 | 내 보험 | ②와 같은 계산에 이미 받은 배상금까지 공제. 가해 차량이 책임보험만·무보험·뺑소니일 때만 | 제20조 |
| ④ | 자동차상해 | 내 보험 | 구분별 실제손해액(과실상계 없음) − (①+②+③+제3자에게서 받은 금액) → 구분별 가입금액 | 자동차상해 특별약관 2.(2) |
| ④ | 자기신체사고 | 내 보험 | 공제액이 없으면 부상은 실제 치료비, 후유장애는 급별 보험금액, 사망은 가입금액. 공제액이 있으면 실제손해액 − 공제액. 모두 급별 한도까지 | 제15조, 제16조 |

- 자동차상해와 자기신체사고는 둘 중 하나만 계산한다(특별약관이 자기신체사고를 대체).
- 이 사람의 과실이 100%이거나 상대 차량이 없으면 ①②③은 "해당 없음"이고 ④만 계산한다.
- 상대방의 대인배상Ⅱ 가입금액을 모르면 ②는 "상대방 계약 확인 필요"이고, ④의 최소는 ②가 무한일 때의 값, 예상·최대는 ①만 뺀 값이다. 내 증권의 한도를 대신 쓰지 않는다.
- 상대방 쪽 사람에게는 내 보험의 ①②만 계산하고, 받는 사람 묶음을 `others`로 표시한다.
- 일용근로자 임금(간병비, 가사종사자 휴업손해, 소득 증명이 없는 사람의 상실수익액)은 약관에 숫자가 없다. `data/rules/daily-wage.json`에 값·출처·공표일·적용 시작일을 사람이 넣는다. 값이 비어 있으면 그 줄만 빼고 계산하며 그 줄과 칸에 "일용근로자 임금 입력 필요"(`daily_wage_required`)를 붙인다.
- 부상 위자료와 후유장애 위자료가 함께 생기면 최소·예상은 둘 중 큰 금액 하나만, 최대는 둘 다 더한 금액이다. 부상 위자료 줄과 칸에 "해석에 따라 금액 차이 있음"(`interpretation_varies`)을 붙인다. 더해지는 금액(둘 중 작은 쪽)은 부상 위자료 줄의 최대값에 둔다.

아직 다루지 않는 것: 내 차 동승자가 내 보험의 대인배상으로 보상받는 경우와 동승자 감액(별표5), 가정간호비, 7세 미만 자녀의 간병비, 19세 미만의 상실수익액, 정년이 따로 있거나 농어업인(70세)인 경우, 부상 뒤 사망·후유장애가 겹칠 때의 책임보험 한도 조정, 여러 피해자가 한도를 나눠 쓰는 경우, 기왕증, 비용(손해방지비용 등).

### 차량 담보와 특약 (v1 7단계에서 구현)

차량 한 대의 손해 항목(수리비 또는 교환가액, 대차료, 휴차료, 시세하락손해, 견인비용)은 `property-ledger.ts`가 한 번만 만들고, `vehicle.ts`가 아래 순서로 계산한다. 뒤 담보가 앞 담보의 금액을 빼므로 계산된 칸끼리 겹치지 않는다.

| 순서 | 담보 | 누구의 보험 | 계산 | 근거 |
|---|---|---|---|---|
| ① | 대물배상 | 상대 차량(상대방 쪽 차량이면 내 보험) | 손해액 합계 × (100 − 이 차량 쪽 과실)% → 가입금액. 수리비는 차량가액의 120%(내용연수 경과 등 130%)까지, 대차료는 25일(정비 160시간 초과 30일, 전손 10일)·렌트하지 않으면 35%, 휴차료는 30일(전손 10일), 시세하락손해는 출고 5년 이하이고 수리비가 차량가액의 20%를 넘을 때 수리비의 20·15·10% | 제10조, 별표2, 별표4 |
| ② | 자기차량손해 | 내 보험 | min(수리비 또는 전손 가액, 가입금액, 차량가액) − ①이 처리하는 수리비 − 자기부담금. 자기부담금은 남은 금액(내 과실분) × 비율을 증권의 최소·최대 사이로. 전손이거나 가입금액 전액 이상이면 빼지 않음. 본인 과실을 다시 곱하지 않음 | 제24조 |
| ③ | 렌트비용지원 특약 | 내 보험 | ②가 지급될 때만. 1일 요금을 차종별 한도까지 × 일수(30일, 전손 10일) − ①이 처리하는 대차료. 렌트하지 않으면 요금과 한도의 35% | 렌트비용지원 특별약관 |
| – | 법률비용 지원 특약 | 내 보험 | 형사합의금(가입 유형 × 피해자 상해급수 한도), 변호사선임비용(5백만원), 벌금(2천만원, 어린이 보호구역 3천만원)을 실제 부담액과 한도 중 작은 금액으로 | 법률비용 지원 특별약관 |
| – | 그 밖의 특약 | – | 금액을 만들지 않고 "증권에 있으나 계산 규칙 미등록"으로 표시. 합계에 넣지 않음 | – |

- 상대방 대물배상 가입금액을 모르면 ①은 "상대방 계약 확인 필요"이고, ②③의 최소는 상대방이 과실분을 모두 처리할 때의 값, 예상·최대는 처리분을 빼지 않은 값이다.
- 자기부담금의 비율·최소·최대는 증권의 값을 쓴다. 약관이 안내하는 조합표(`ownDamage.deductible.options`)에 없으면 `deductible_not_in_table` 표시를 붙인다.
- 보험 종류: `lib/rules/person-rules.ts`의 `rulesFor(productLine)`가 개인용 규칙을 바탕으로 하고 `data/rules/{motorcycle,business,commercial}.json`(개인용과 다른 점만)으로 덮어쓴다. 세 약관 PDF에 개정일이 없어 이 파일들의 항목은 모두 `needs_check`다. 이륜차 약관에는 자동차상해·렌트비용지원 특약이 없고, 영업용 약관에는 렌트비용지원 특약이 없다(무보험자동차상해는 특약). 별표2 문구는 네 약관이 같다.
- 아직 다루지 않는 것: 금액 문자열 변환(`money.ts`)과 증권 JSON 스키마, 운전자 범위·음주·무면허 등 면책(`applicability`), 사고부담금, 영업손실, 자기차량손해의 잔존물·부품 감가 공제와 비용(견인 등), 여러 피해물이 대물 한도를 나눠 쓰는 경우, 업무용·영업용·이륜차 약관의 특약 한도 대조.

### 결과 화면·설명·읽어주기·내려받기 (v1 8단계에서 구현)

- 화면 입력 → 엔진: `lib/draft/to-claim.ts`가 입력 초안을 엔진 입력으로 바꾸고 `lib/result/compute.ts`가 행렬과 합계를 만든다. 브라우저 안에서 계산하며 서버로 보내지 않는다. 증권의 금액 표현은 `lib/engine/money.ts`가 원 단위로 바꾼다("부상 3천만원" → 30,000,000). 바꾸지 못하면 null이라 "정보 부족"이 된다.
- 상대방 보험(가입 여부, 대인배상Ⅱ·대물배상 가입금액)은 "사고 말하기" 화면에서 따로 받는다. 내 증권의 한도를 대신 쓰지 않는다.
- 결과 화면: 맨 위에 내가 받을 총 예상 보험금(예상값 크게, 최소~최대), 상대방에게 지급될 금액은 따로. 사람별 탭 → 담보별 카드(금액, 항목별 내역, 부족 정보 버튼, "왜 이 금액?", 근거 조항). 부족 정보 버튼은 `lib/result/field-link.ts`가 정한 입력 칸(`#f-…`)으로 이동한다.
- "왜 이 금액?": 기본은 엔진 내역으로 만든 문장(`lib/explain/default.ts`). 이용권이 있으면(v2) `/api/explain`으로 쉬운 말 설명을 받는다. 브라우저가 보낸 입력으로 서버가 같은 엔진으로 다시 계산한 칸만 설명하고(저장하지 않는다), LLM은 금액을 `{{키}}` 자리표시로만 쓴다. 자리표시 밖에 숫자나 한글 금액이 있거나 없는 키를 쓰면 설명을 버리고 기본 문장을 돌려준다(`lib/explain/llm.ts`).
- 읽어주기: 결과 요약과 증권에서 읽은 내용을 `/api/tts`(OpenAI 음성 합성, mp3)로 재생한다. 재생·멈춤·속도(0.8·1·1.25·1.5배). 이름·차량번호·증권번호는 글에 넣지 않는다(v2는 애초에 없다).
- 내려받기(브라우저에서 만든다): 엑셀은 총괄표 + 사람별 + 근거 시트(값만, 수식 없음). PDF는 요약 1~2쪽으로, 기기의 글꼴로 쪽을 그림으로 그려 넣는다(글자를 긁어 복사할 수 없다).
- 결과 저장(v2): 서버에 저장하지 않는다. 브라우저에 입력과 함께 엔진 버전, 규칙 파일 버전(`data/rules/version.json`의 해시, `scripts/rules-version.mjs`가 만든다)을 둔다. 합계는 저장하지 않고 열 때마다 다시 계산한다. 규칙 버전이 바뀌었으면 "규칙이 바뀌어 다시 계산했습니다"를 알린다. 규칙 json을 고치면 이 스크립트를 다시 돌려야 하며, 돌리지 않으면 테스트가 실패한다.
- v1에서 아직 하지 않았던 것: 법률비용(형사합의금 등)·후유장애·사망·상대방 차량의 입력 칸, 운전자 범위·음주 등 면책 확인.

### 약관 대조 (v1 규칙 보완에서 구현)

`scripts/check-product-terms.mjs`가 약관 PDF의 글자에서 지급기준 문구와 표를 직접 찾아 개인용 규칙 값과 견주고, 결과를 `data/rules/product-check.json`에 적는다(손으로 옮기지 않는다). 대조 방법이 맞는지는 개인용 약관(2025-11-26)에서 52개 대조가 모두 일치하는 것으로 확인한다.

| 약관 | 결과 | 개인용과 다른 점 |
|---|---|---|
| 업무용 | 52개 모두 일치 | 없음 |
| 영업용 | 50개 중 46개 일치 | 무보험자동차상해가 보통약관에 없음(특별약관), 렌트비용지원 특별약관 없음, 법률비용 가입 유형이 기본형·고보장형 둘(고보장형 = 개인용 고급형과 같은 값) |
| 이륜차 | 49개 중 45개 일치 | 자동차상해·렌트비용지원 특별약관 없음, 법률비용에 가입 유형 구분 없음(개인용 기본형과 같은 값), 벌금비용에 어린이 보호구역 3,000만원 단서 없음 |

- 다른 점만 `data/rules/{business,commercial,motorcycle}.json`에 둔다. 같은 값임을 확인한 항목은 `rulesFor()`가 그 약관의 쪽 번호를 출처로 붙인다.
- 세 약관 PDF에는 개정일이 없다. 그래서 값이 같아도 확인 상태는 `needs_check`다. `data/rules/product-revisions.json`에 개정일과 확인 근거를 넣으면 대조된 항목이 그 날짜부터 적용되는 확정 값이 된다.
- 대조하지 않은 것: 약관 본문이 아닌 안내 쪽에서 읽은 값(대인배상Ⅰ 사망 한도 안내, 자기부담금 조합표), 조항 문구만 옮긴 특약 설명, 개인용에서도 `needs_check`인 항목.
- 대조하다 본 것(지금 엔진이 쓰지 않는 부분): 업무용·영업용·이륜차 약관의 "현역병 등 군복무 해당자" 소득 기준 문구가 개인용(2025-11-26)과 다르다. 세 약관이 개인용과 다른 시점의 판일 수 있다.
- 표준약관: `docs/source/`에 금융감독원 표준약관 PDF를 넣고 같은 스크립트를 돌리면 "standard"로 대조되고 `tests/rule-sources.test.ts`의 건너뛴 테스트가 켜진다. PDF는 아직 없다.
- 일용근로자 임금: `data/rules/daily-wage.json`의 값은 아직 비어 있다. 공표 원자료를 확인하지 못해 넣지 않았다.

### 법령·판례 근거 (v1 법령 연결 단계에서 구현)

- 국가법령정보센터 Open API는 서버(`lib/law/client.ts`)에서만 부른다. 인증값(`LAW_API_OC`)은 응답에 싣지 않는다. 판례 응답의 상세 링크에는 인증값이 들어 있어 쓰지 않고, 공개 화면 주소(`law.go.kr/precInfoP.do?precSeq=…`)를 만들어 준다.
- 쓰는 API: 조문 `lawService.do?target=lawjosub&ID=<법령ID>&JO=<조 4자리+가지 2자리>`, 판례 검색 `lawSearch.do?target=prec&search=2&query=…`. 응답은 항·호가 하나면 객체, 여럿이면 배열로 온다. 인증에 실패해도 200으로 안내문이 오므로 모양으로 확인한다.
- 조문과 검색어는 `lib/law/catalog.ts`의 목록에 있는 것만 받는다. 아무 값이나 받아 주지 않으므로 로그인 없이 열어 두었다(공개 자료, 개인정보를 보내지 않음).
- 결과는 서버 메모리에 24시간 둔다(실패는 저장하지 않음). 응답에도 `s-maxage=86400`을 붙인다. 서버 인스턴스가 바뀌면 다시 부른다. DB 캐시 테이블은 만들지 않았다.
- 화면: 담보 카드의 "근거 조항"을 펼치면 관련 법령 목록이 있고 "법령 보기"로 원문을 편다(대인배상Ⅰ → 시행령 제3조 책임보험금 한도 등). 상대가 있는 사고에서 과실이 0%·100%가 아니거나 비어 있으면 "과실비율 참고 판례" 카드가 나온다. 사고 유형에 맞는 검색어를 누르면 최근 판례 10건을 보여 준다.
- 실패하면 화면은 그대로 두고 "법령 정보를 불러오지 못했습니다"만 보여 준다(인증값 없음, 연결 실패, 모양이 다른 응답 모두 같은 문구).
- 한계: 조문은 지금 시행 중인 내용이다. 사고일 당시의 조문을 고르지 않는다(화면에 그렇게 적었다). 시행령 별표 1·2(급별 한도표)의 원문은 이 API의 조문 조회에 들어 있지 않아 보여 주지 않는다.

### 통합 점검 방법 (v1 통합 점검 단계에서 구현)

- `scripts/e2e/mock-services.mjs`: v1은 Supabase(로그인·DB)와 LLM·음성 제공자를 흉내 냈다. v2는 Supabase 부분을 지우고 LLM·음성 제공자와 Turnstile `siteverify`만 흉내 낸다. `/__debug/state`로 제공자가 받은 요청을 볼 수 있다.
- `scripts/e2e/mock-fetch.mjs`: 서버 프로세스에 미리 불러와 `api.anthropic.com`·`api.openai.com`으로 가는 요청을 가짜 서비스로 돌린다. 운영 코드는 건드리지 않는다.
- 실행 방법은 `mock-services.mjs` 맨 위 주석에 있다. 개발 서버가 이미 떠 있으면 `npm run build` 뒤 `next start -p <다른 포트>`로 띄운다.
- v1 점검에서 확인한 것: 주민등록번호 뒷자리가 화면 저장소·DB·제공자 요청 어디에도 없음, 읽어주기·설명 요청에 이름·차량번호·증권번호 없음, 로그인이 없으면 유료 API가 제공자를 부르기 전에 401. v2에서 확인할 것: 이용권이 없으면 제공자를 부르기 전에 401, 증권 판독 응답·브라우저 저장소·제공자 요청 어디에도 가릴 항목 9가지가 없음.

### 최소·예상·최대를 만드는 방법

| 값이 갈리는 원인 | 최소 | 예상 | 최대 |
|---|---|---|---|
| 상해급수가 범위로만 정해짐 | 가장 낮은 금액이 나오는 급수 | 사용자가 고른 급수, 없으면 가운데 | 가장 높은 금액이 나오는 급수 |
| 과실비율을 범위로 입력 | 내 과실이 큰 쪽 | 가운데 값 또는 사용자가 고른 값 | 내 과실이 작은 쪽 |
| 휴업손해에 소득 증빙이 없음 | 0 | 규칙이 정한 기본 소득 기준 | 입력한 소득 기준 |
| 공제할 금액(다른 담보 수령액)을 모름 | 공제 가능한 최대를 뺀 값 | 공제 없음으로 계산하고 표시 | 공제 없음 |
| 향후치료비 등 추정 입력 | 0 | 입력값 | 입력값 |
| 부상 위자료와 후유장애 위자료가 겹침 | 큰 금액 하나만 | 큰 금액 하나만 | 둘 다 합산 |

모든 칸에서 최소 ≤ 예상 ≤ 최대가 성립해야 한다. 테스트로 확인한다.

    driver-charges.json       사고부담금

  business.json             업무용: 개인용과 다른 점만
  commercial.json           영업용: 개인용과 다른 점만

```json
{
  "id": "solatium.injury.grade7",
  "value": null,
  "unit": "KRW",
  "productLines": ["personal", "business", "commercial", "motorcycle"],
  "effectiveFrom": "2025-10-01",
  "effectiveTo": null,
  "basis": {
    "sourceId": "hi-personal-20251126",
    "source": "현대해상 개인용 약관 2025-11-26 개정 별표 79쪽",
    "document": "하이카 개인용자동차보험 약관",
    "appendix": "별표1 대인배상 지급기준",
    "clause": "나. 부상 2. 위자료",

```

- `status`는 `confirmed` 또는 `needs_check` 둘 중 하나다.
- `basis.source`는 출처 표기다. 현대해상 약관에서 읽은 값은 "현대해상 개인용 약관 2025-11-26 개정 별표 ○쪽"으로 적는다(별표가 아닌 약관 본문·특별약관·안내 쪽에서 읽은 6개는 "본문 ○쪽"). 표준약관 원문과 대조하는 테스트 자리는 `tests/rule-sources.test.ts`에 skip으로 있다. `docs/source/`에 표준약관 PDF가 들어오면 채운다.
- `needs_check` 항목은 `value`가 비어 있을 수 있다. 비어 있으면 그 항목을 쓰는 칸은 "약관 확인 필요"가 된다. 값이 있는 `needs_check` 항목을 쓰면 금액은 계산하되 칸에 "약관 확인 필요" 표시를 붙인다.
- 같은 id에 적용 기간이 다른 항목이 여럿 있을 수 있다. 사고일이 속한 기간의 항목을 쓴다.
- 규칙 파일도 zod 스키마로 검증하고, 빌드할 때 스키마에 맞지 않으면 실패하게 한다.
- `rules_version`은 규칙 파일 전체의 해시다. 결과에 기록해 나중에 어떤 규칙으로 계산했는지 알 수 있게 한다.

## 7. 데이터 스키마

실제 정의는 `lib/schemas/*.ts`의 zod 스키마이고 아래는 모양을 보여주는 예시다. 공통 약속:

- 금액은 원 단위 정수. 모르면 `null`, 없다고 확인했으면 `0`.
- 날짜는 `YYYY-MM-DD`.
- LLM이 채운 값에는 `origin: "llm"`과 `confirmed: false`가 붙고, 사용자가 확인하면 `confirmed: true`가 된다. 엔진은 확인된 값만 쓴다.
- 원문에서 읽은 금액은 `{ "raw": "3천만원", "won": 30000000 }`처럼 원문과 변환값을 함께 둔다. `won`은 `money.ts`가 채운다.

## 8. 작업 단계

각 단계 끝에 `compass/`에서 `npm run build`와 `npm test`를 통과시키고, `compass/`만 커밋한 뒤 멈춘다.

### v1에서 끝난 것 (다시 만들지 않는다)

설계, 화면 골격, 증권 읽기(PDF·HEIC·JPG·PNG), 음성 입력·사실 추출·상해급수 후보, 계산 엔진 A(사람 담보, 손 검산 35건)·B(차량·특약·이륜차·합산 불변식), 결과 화면·설명·읽어주기·내려받기, 업무용·영업용·이륜차 약관 대조, 법령·판례 연결, 통합 점검, 합계 점검. 자세한 기록은 v1의 `git log`와 6절의 "(v1 …에서 구현)" 항목에 있다. v1의 로그인·DB·사용량 한도는 v2에서 걷어 낸다.

## 10. 진행 기록

2026-10-15부터 사용자 지시로 배포까지 묻지 않고 진행한다. 스스로 정한 것과 그 이유를 한 줄씩 남긴다(판단 기준: 신뢰 > 개인정보 보호 > 비용 > 개발 속도).

- [7·8단계] 생년월일 대신 사고일의 만 나이(`age`)를 받는다. 나이가 들어가는 항목(사망·후유장애 위자료의 65세 기준, 취업가능월수)은 생일 1년 폭의 양 끝으로 최소·최대를, 가운데(생일이 반년 전)로 예상을 낸다(`lib/engine/age.ts`). 이유: 생년월일은 신원정보이고, 범위로 내면 v1 손 검산 값이 모두 범위 안에 든다(테스트로 확인).
- [7단계] 3단계 저장 방식은 유지하되, 7단계 전 초안의 `birthDate`는 읽을 때 사고일 기준 만 나이로 바꾸고 버린다(`lib/draft/store.ts`의 최소 수정). 이유: 바꾸지 않으면 strict 검증 때문에 기존 기록이 "읽을 수 없는 기록"이 된다.
- [8단계] 엔진이 만든 행렬로 fast-check 불변식(무작위 만 나이·사망·후유장애·과실)을 더했다. 기존 불변식 테스트는 그대로 둔다.
- [5단계] 증권 판독 스키마에서 신원 칸을 모두 뺐다(주민번호로 생년월일·성별을 만들던 v1 처리도 없앴다). 화면 응답은 `strict`이고 `redacted`(가린 건수)만 더 싣는다. 이유: v2는 보험 정보만 쓴다.
- [5단계] 주민등록번호는 앞 6자리까지 함께 가린다(v1은 앞자리를 남겼다). 이유: 앞자리가 곧 생년월일이다.
- [5단계] 증권 파일 이름은 저장하지 않고 "사진"·"PDF의 글자" 같은 읽은 방법만 남긴다. 이유: 파일 이름에 사람 이름이 들어 있는 경우가 많다.
- [5단계] 사진은 올리기 전에 칠해 가리는 화면(`components/MaskEditor.tsx`)을 거친다. 브라우저가 그리지 못하는 사진(크롬의 HEIC 등)은 칠할 수 없다고 알리고, 캡처해 올리기와 그대로 올리기 중에서 고르게 했다. 이유: 막아 버리면 아이폰 사용자가 쓸 수 없다. 그대로 올려도 비전 지시와 결과 가리기가 남는다.
